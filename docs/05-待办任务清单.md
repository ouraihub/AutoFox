### 连带修掉一个会挂死每次下载的生产 bug

这次验证卡了很久，根因不是环境问题，而是 `queue.rs::start` 自死锁：它在持有 `records` 的 `MutexGuard` 时调用 `persist`，而 `persist` 经 `list` 再次 `lock` 同一个 `std::sync::Mutex`。`Mutex` 不可重入，于是**任何一次下载在第一行就永久阻塞**——`download_direct` 的 `state.start()` 在所有日志之前，所以现象是"命令没到 Rust"：无日志、无目录、Promise 既不 resolve 也不 reject。`mux_streams` 走同一个 `start`，同样中招。`tasks.json` 从来不存在，正是因为 `persist` 一次都没写完。

修法不是"在 persist 前 drop guard"，而是把加锁区与落盘拆开：新增私有 `register`（持锁，只动 `BTreeMap`，够不到第二次 `lock`），`start` = `register` + `persist`。这样死锁形状在结构上不可表达，而不是靠记得手动 drop。同时把硬编码的 `>= 4` 提为 `MAX_ACTIVE_TASKS`。

回归测试 `queue_tests.rs::register_releases_the_lock_before_returning` 在子线程跑 `register` 然后调 `list`（`persist` 真正做的那一次调用），10 秒超时判定死锁——直接断言会把整个测试套件挂住而不是报失败。已验证该测试对旧形状失败（`register then list did not finish within 10s`）、对新代码通过。另外 4 个测试覆盖并发上限、终态释放槽位、暂停释放槽位。

曾经的错误判断记录在此以免重复：我一度归因为"SvelteKit 给 `window.fetch` 打补丁破坏了 Tauri IPC"。那是假象——同一份日志里 `extract: probing` 和 `mux: muxing` 都是异步 command 且都到过 Rust，证明异步 IPC 通道本身是好的。

顺带修掉一个真实但未触发的 CSP 缺口：`connect-src` 只列了 `'self'` 与 `asset:`，没有 IPC 源。Tauri 2 在 Windows 上 `invoke` 走 `http://ipc.localhost`，与 `'self'`（`http://tauri.localhost`）不同源，会被 CSP 拦掉并回落到 postMessage。已补 `ipc: http://ipc.localhost`。

另记一个我自己踩的坑：直接 `cargo run --no-default-features` 跑二进制**不会**加载已构建的 `frontendDist`，而是去连 `devUrl`；dev server 不在时页面空白（`ERR_CONNECTION_REFUSED`），JS 一行都不执行。要验 packaged 行为必须走 `pnpm build:app`。

**留给 P0.4 的已知缺陷**：`load` 把上次进程死亡时遗留的 `downloading` 记录原样恢复。那个任务已随进程消失，却永久占着一个并发槽，且界面上永远显示"下载中"。启动时应把非终态记录改写为 `Failed` 或 `Paused`，这属于状态机三件套的范围。

### P0.2 无代理设置

全仓库 0 处代理相关代码。对需要代理才能访问 YouTube 的网络环境，应用直接不可用——这不是体验问题而是可用性问题。

三条路径都要覆盖，且必须共用同一设置值，否则会出现"能解析但下不动"的割裂。下表的 flag 与 API 形状已对本机随包二进制和 vendored 源码核实过，不是推测：

| 路径 | 落点与已核实形状 |
|---|---|
| 解析 | yt-dlp `--proxy URL`。`yt-dlp.exe --help` 原文：支持 HTTP/HTTPS/SOCKS，SOCKS 需带 scheme（`socks5://user:pass@127.0.0.1:1080/`），传空串表示直连。加在 `extract/mod.rs:292` 的 argv 里 |
| 直链下载 | `download.rs:166` 的 `Client::new()` 换成 `Client::builder().proxy(p)`。`Proxy::all()` 返回 `crate::Result<Proxy>`（**可失败，要处理**，非裸值），`ClientBuilder::proxy()` 在 `async_impl/client.rs:1423` |
| HLS/DASH | ffmpeg `-http_proxy <string>`（"set HTTP proxy to tunnel through"）。它是 **protocol option，必须放在输入 URL 之前**。`mux.rs` 两处 `Command::new(ffmpeg)`（:138、:350）都要加，漏一处只有部分流媒体可用 |

**一个必须先决策的约束——reqwest 侧当前不支持 SOCKS5。** 项目的 reqwest 是 `default-features = false`，未启用 `socks`。vendored 源码里 socks scheme 能被 `Proxy` 解析（`proxy.rs:734-740`），但实际连接路径全部在 `#[cfg(feature = "socks")]` 之后（`connect.rs:81/104/216/329`）。即：用户填 `socks5://127.0.0.1:1080` 时 yt-dlp 解析能走通、直链下载走不通——正是本条要避免的割裂，而且表现为"解析出格式却下载失败"，极难排查。

两个选项：(a) 给 reqwest 加 `socks` feature，代价是要走一遍 `.pnpm/crates/crates-io` 重新 vendor 流程（`.cargo/config.toml` 把 crates-io 替换成本地目录，加依赖/feature 都得重新 vendor）；(b) 首版只支持 HTTP/HTTPS 代理，设置项校验拒绝 socks scheme 并给出明确提示。

建议 (a)。国内本地代理客户端常见形态就是 SOCKS5，(b) 会让相当一部分用户填了看似合法的地址然后下载失败。

另外 yt-dlp 还有 `--geo-verification-proxy`，与 `--proxy` 分离（前者只验 IP，后者才走实际下载）。首版不暴露，但设置项命名别占用 "geo" 语义，留出余地。

验收：配一个本地 HTTP 代理 → 解析 + 直链下载 + 一条 HLS 均成功；关掉代理后同一 URL 报 `network`。若选 (a)，同一组验收再跑一遍 SOCKS5。

### P0.3 暂停后无法恢复（确定性 bug）

界面有暂停按钮，点下去显示"已取消"，再点恢复报错。这不是缺功能，是已有功能坏了，所以排进 P0。

链路：

1. `pause_task` → `cancel(task_id, paused: true)`，状态置 `Paused`，cancel 标志置 true。
2. 下载循环在 `download.rs:221` 读到标志，`return Err(Cancelled)`。
3. `download.rs:112` 的 `finish()` 按 `error.code == Cancelled` 无条件写入 `TaskState::Cancelled`，**覆盖掉刚设的 `Paused`**。
4. 用户点恢复，`resume()` 检查 `state != Paused` → 返回 `errors.taskNotPaused`。

不是竞态，每次必然发生：`finish` 无条件覆写状态，没有"暂停请求中"的判别。

三处要改，比"改两行"大一个量级：

- **`finish` 的覆写规则。** 根因是 `finish()` 直接 `record.summary.state = state`，不看当前状态。AutoAnt 已解决过同一问题，`src-tauri/src/runner/slot.rs` 的注释就是规则本身："The registry is the single authority on lifecycle transitions. `finish` only succeeds for a run that is still `Running` and every later attempt is rejected." 采用同一规则：`finish` 只在任务处于它所拥有的非终态时生效，处于 `Paused` 时拒绝覆写。这条同时消掉"完成撞取消"的竞态。
- **`resume` 没有重启下载循环。** 它只把标志置回 false 并改状态，而循环在第 2 步已退出。必须重新 spawn。
- **原始请求没有被持久化。** 这是上一版清单低估的部分：`TaskSummary` 只有 `task_id`/`kind`/`state`/`output_path`/`error_key` 五个字段，**没有 URL、输出目录、文件名**。`resume` 即使修好状态也无从重启。需要给 `TaskRecord` 加可持久化的重启参数（source_url + format_id + media_url + 输出目录 + 文件名）。存 `source_url` 与 `format_id` 而不只存 `media_url`，是因为提取器给的 CDN 直链通常带签名与有效期，过期后 `Range` 会 403，那时要用 `source_url` 重新解析、按 `format_id` 重取直链。

续传本身是安全的，已核实：`download.rs:193` 的 `append` 要求状态码为 206，服务器忽略 `Range` 返回 200 时 `append` 为 false，走 `File::create` 截断重下，不会静默追加损坏。缺的是资源同一性校验（无 `ETag`/`Content-Length` 比对），同一 URL 内容已变且服务器仍返回 206 时会拼出坏文件——这条可随 P0.3 一起补。

验收：下载中点暂停 → 状态显示 `Paused` 且 `.part` 保留 → 点恢复 → 字节数从暂停处继续增长并最终完成，文件可播放。

### P0.4 合流任务的取消是假的

`mux.rs:67` 写的是 `let (task_id, _cancel) = state.start("stream", ...)`——cancel 令牌被绑成下划线变量，**全文件再无一处读取**（`grep -nE 'is_cancelled|kill' mux.rs` 零命中）。

后果：用户对一个合流任务点取消，`cancel()` 把状态改成 `Cancelled`、标志置 true，但 ffmpeg 子进程继续跑到底，然后 `finish` 把状态改回 `Done`。界面先显示已取消、随后跳成已完成，进程从未被终止。

修法与 P0.3 同批做，因为它们共用 `finish` 的状态转移规则：

- 合流循环需要读 cancel 标志，并真正终止 ffmpeg 子进程（`Child::kill`）。
- 终止后清理不完整的输出文件——`-c copy` 中途被杀留下的容器缺尾部索引，既不可播也不可续。

**合流任务不支持暂停**（定案，不留待确认）：`mux.rs` 只有 `Done`/`Failed` 两个终态，且 ffmpeg 无通用"续接封装"能力。UI 对 `kind == "stream"` 的任务禁用暂停按钮，取消语义为丢弃中间产物。

验收：合流进行中点取消 → ffmpeg 进程消失（任务管理器可验）→ 状态停在 `Cancelled` 不再跳变 → 不完整输出文件已清理。

### P0.5 重启后遗留任务永久停在"下载中"

`load()` 把 `tasks.json` 里的摘要**原样插入**注册表，没有任何状态规范化。上次退出时处于 `Downloading` 的任务，重启后仍是 `Downloading`，但没有任何代码重新 spawn 它的下载循环——它会永久显示"下载中"且字节数不动，用户既不能恢复也不能重试。

这条直接否掉 [04](04-实施计划.md) 阶段 4 的验收声明"应用重启后未完成任务恢复并续传成功"：该验收目前不可能成立。

修法（依赖 P0.3 的重启参数持久化）：`load()` 应把遗留的 `Downloading` 规范化为 `Paused`（`.part` 已在磁盘上，语义正好是"可恢复"），由用户或自动恢复逻辑重新拉起。

验收：下载中强杀应用 → 重启 → 任务显示 `Paused` → 点恢复 → 从已落盘字节继续并完成。

## P1 — 架构性缺口

### P1.1 并发上限是拒绝，不是排队

`queue.rs:122-135`：活跃任务数 `>= 4` 时 `start()` 直接返回 `ErrorCode::Busy`。用户连点第 5 个下载会看到报错，而不是任务进入等待。

需要的是真正的队列：超限任务置为 `Queued`，有任务终止时自动提取下一个启动。`TaskState` 目前只有 `Downloading` / `Paused` / `Done` / `Failed` / `Cancelled`，没有 `Queued`；`src/lib/ipc/client.ts` 的同名联合类型同样缺它，两侧都要加。

**注意现有形状是调用方驱动的**：`download.rs:87` 拿 `start()` 的返回，`:92` 自己 `await` 下载循环。所以排队不能只改 `start()` 里的判断——调用方拿不到许可仍会往下跑。两条路：

- **(a) 信号量许可**：`start()` 改 async，先置 `Queued`，await 一个 `tokio::sync::Semaphore` 许可，拿到后转 `Downloading`，guard 随任务作用域释放（异常/取消路径自动归还）。已核实 `tokio` 的 features 含 `sync`，无需改依赖。
- **(b) 注册表自己 spawn**，command 改 fire-and-forget。

建议 (a)：`download_direct` 已是 `async fn`，UI 调用形状不变；(b) 要重写全部 command 的返回契约。

这条排在 P1 首位是因为它决定 `TaskRegistry` 的形状——先做重试或可配置并发都会被它推翻一次。它也依赖 P0.3 先把 `finish` 的状态转移规则定清楚，否则排队调度会建在一个会被覆写的状态机上。

顺带记一处与 AutoAnt 的**有意分歧**：AutoAnt `runner/slot.rs` 明确选了 `Busy` 而非排队（注释原文 "exceeding it returns `Busy` rather than queueing without bound"，上限 8/窗口）。那对 API 请求是对的——短、交互式，排队只积压过期请求。下载任务长且批量，用户预期是排队。所以此处不照搬。

验收：连续提交 6 个下载 → 4 个 `Downloading`、2 个 `Queued`；取消一个活跃任务 → 一个排队任务自动转为 `Downloading`。

### P1.2 并发数不可配置

字面量 `4` 写在 `queue.rs:126`。`settings.rs` 无对应字段，界面也无入口。依赖 P1.1 完成后再接设置值。

验收：设置改为 2 → 提交 4 个下载 → 同时只有 2 个在跑。

### P1.3 无失败重试

网络抖动导致的失败直接终结任务，用户只能手动重来。`ipc.rs` 的 `IpcError` 已有 `retryable: bool` 字段可作判据——它已经区分了"重试可能成功"和"重试无意义"，重试逻辑应当读这个字段而不是另建一套判断。

需要指数退避和次数上限，避免对已下线的资源反复打。

验收：下载中途断网 → 日志显示退避重试；恢复网络后任务继续并完成，`Range` 起点等于已落盘字节。

## P2 — 工程基建

### P2.3 无 i18n 层

`src/lib/i18n` 不存在，`+page.svelte` 有 57 行含硬编码中文。这条排在 CI 之前，因为每天新增的界面都在加硬编码字符串，越晚做迁移面越大。

AutoAnt 的 `src/lib/i18n/locale.svelte.ts` + `messages/` 结构可直接照搬（runes store + 消息表）。

后端 `IpcError` 已有 `message_key: &'static str`（如 `errors.internal`），但前端**根本没消费它**：`client.ts:147` 的 `errorMessage()` 依次回退到 `error.message`、`detail`、原始字符串，而 `detail` 是英文诊断原文。所以当前错误提示要么是英文，要么是调用点写死的中文兜底（如 `+page.svelte:154` 的 `'下载失败，请重试。'`）。i18n 层必须改成按 `message_key` 查表，`detail` 只作日志用，不进界面。

现有 21 个 key 的完整清单（`grep -rhoE 'message_key: "[^"]+"' src-tauri/src | sort -u`），消息表首版就该覆盖全，缺一个就会在出错时露出空白或英文：

```
errors.cancelled              errors.noFormats
errors.downloadFailed         errors.probeTimedOut
errors.ffmpegMissing          errors.taskLimit
errors.fileWriteFailed        errors.taskNotFound
errors.internal               errors.taskNotPaused
errors.invalidBackendJson     errors.unsupportedContainer
errors.invalidDownloadRequest errors.ytdlpLaunchFailed
errors.invalidMuxRequest      errors.ytdlpMissing
errors.invalidSettingsVersion
errors.invalidUrl
errors.muxFailed
errors.muxTimedOut
errors.nativeBackendAbsent
```

其中 `errors.taskLimit` 在 P1.1 落地后语义会变（不再是"拒绝"而是"排队"），`errors.taskNotPaused` 在 P0.3 修好后应当不再出现在正常路径——做 i18n 时这两条的文案别写死成当前行为。

验收：切换语言 → 界面文案与后端错误提示同时切换；`grep -cP '[\x{4e00}-\x{9fff}]' src/routes/+page.svelte` 降到 0。

### P2.1 无 CI

`.github/workflows` 不存在，`pnpm verify` 全靠手动跑。

门禁内容按 [04 §质量门禁](04-实施计划.md) 已定义的组合：`check` + `lint` + `test:rust` + `clippy -D warnings` + `fmt`。Windows runner，因为便携 MSVC 和 `ReadDirectoryChangesW` 都是 Windows 专属；runner 上先跑 `ilammy/msvc-dev-cmd`，`pnpm install` 后再 `call node_modules\@ouraihub\desktop-kit\msvc\msvc-env.bat`。

验收：提一个故意含 clippy 警告的 PR → CI 红；修掉 → CI 绿。

### P2.2 前端零测试，且格式分组逻辑无测试

这是两个相邻但不同的缺口，别混在一起做。

**前端零测试。** 35 个 Rust 测试覆盖后端，Svelte 组件和 `src/lib/ipc/client.ts` 零覆盖。`package.json` 里没有 `vitest`，只有 `test:rust`。首个该覆盖的契约是 IPC 载荷映射：`TaskProgress` 的 `percent` 是可选字段，直链下载与 ffmpeg 合流填充的字段不同，前后端字段不匹配的 bug 已经出现过一次——正是这类测试该抓的。

**格式分组逻辑无测试（Rust 侧）。** `extract/options.rs` 的 `build()` 把 yt-dlp 的原始 format 列表（一个 YouTube 视频约 36 行）折叠成用户可选项，是纯函数。该文件现有的 2 个测试只钉 `DeliveryPlan` 的序列化键名（`merge_plan_serializes_the_keys_mux_streams_expects`、`progressive_and_manifest_plans_expose_camel_case_format_id`），没有一个测分组结果。三条已写进代码注释的规则值得表驱动钉住：

- 渐进式流（同时含音视频）在同分辨率下胜出，因为免 ffmpeg 一道；
- `container != "mhtml"` 剔除 storyboard；
- 1080p 以上无 H.264 时容器跟随视频编解码（VP9/AV1 → webm），音轨须与容器匹配（mp4 收 AAC、webm 只收 Opus/Vorbis），无匹配音轨则降级为无音轨清单。

验收：`pnpm test` 跑通且故意把 `percent` 改成必填 → 前端测试变红；`pnpm test:rust` 中新增分组测试，把 `build()` 里的渐进式优先分支去掉 → 测试变红。

## P3 — 后续增强

### P3.1 yt-dlp 无自更新

`tauri.conf.json` 无 `updater` 配置。选 sidecar 架构的前提就是"站点适配由上游负责"，但上游的修复传不到用户手里，这个前提就不成立——YouTube 改一次前端，用户就得等重新打包。

两件事要分清：

- **yt-dlp 二进制更新**：频率高、价值大。yt-dlp 自带 `-U`，但随包分发时通常自行下载替换更可控。
- **AutoFox 应用更新**：频率低。Tauri updater 需要签名密钥和发布端点。

优先做前者：它才是解决"提取器过期"的那一半，且不需要发布基础设施。

验收：手动降级随包 yt-dlp → 应用内触发更新 → 版本号上升，「后端」tab 显示新版本。

### P3.2 字幕未落盘

`extract/` 目录只有 `backend.rs` / `mod.rs` / `options.rs`，没有 `subtitles.rs`；全仓库仅 `options.rs:127` 一处注释提到 thumbnail（用于识别 storyboard 为缩略图表，与字幕无关）。即字幕、缩略图、章节三项都未开始，不是"列出来了但没落盘"。

这条排在最后是因为它是独立增量，不阻塞其他任何一条。

验收：解析一个有字幕的 URL → 勾选字幕 → 产出 `.srt` 与视频同目录同名。

## 建议顺序与理由

| 序 | 任务 | 为什么在这个位置 |
|---|---|---|
| 1 | ~~P0.1 下载目录~~ | **已完成**。纯接线，字段已存在，最快见效 |
| 2 | dev 环境异步 IPC 障碍 | 新增。不修它，P0.3/P0.4/P0.5 的状态机全都无法在真应用里验证，只能靠单元测试——而这三项恰恰是状态机时序问题，单元测试覆盖不到真实窗口生命周期 |
| 3 | P0.3 + P0.4 + P0.5 状态机三件套 | 同一个根因（`finish` 无条件覆写），必须同批做。它们定义的状态转移规则是 P1.1 队列调度的地基 |
| 4 | P0.2 代理 | 决定应用在受限网络下是否可用。先做 SOCKS5 的 (a)/(b) 决策 |
| 5 | P1.1 队列语义 | 决定 `TaskRegistry` 形状，依赖第 3 项的状态机 |
| 6 | P1.2 并发可配 | 依赖 P1.1 |
| 7 | P2.3 i18n | 硬编码文案每天都在增加。消息表需覆盖 22 个 key（P0.1 新增了 `errors.invalidDownloadDirectory`） |
| 8 | P2.1 CI | 前面几条产生了足够的回归面，值得自动化 |
| 9 | P2.2 测试 | 与 CI 配套才有意义。前端零测试的缺口在 P0.1 已经暴露过一次：`resolveDownloadDirectory` 只能用一次性脚本证明 |
| 10 | P1.3 重试 | 建在稳定的队列语义之上 |
| 11 | P3.1 自更新 | 独立增量 |
| 12 | P3.2 字幕 | 独立增量 |

三处顺序与上游审计不同：

- **P0.3/P0.4/P0.5 合并提前到第 3 位。** 审计把"暂停/恢复"列为不存在并排到最后。实际是三个 bug 共享一个根因：`finish()` 直接写 `record.summary.state = state`，不看当前状态。分开修会三次触碰同一个函数；合并做一次，顺便把 P1.1 需要的状态转移规则定死。
- **P0.2 代理让到第 4 位。** 它本身不依赖状态机，但要改 `download.rs` 的 client 构造与 `mux.rs` 的两处 argv——与状态机三件套改动区域重叠，排在后面能避免冲突。
- **P1.3 重试后移。** 依赖 P1.1 的队列语义稳定，提前做会连带改两次。

状态机三件套的状态转移表（实现时按此为准）：

| 当前 | 允许转入 | 拒绝 |
|---|---|---|
| `Queued` | `Downloading`、`Cancelled` | 其余 |
| `Downloading` | `Paused`、`Done`、`Failed`、`Cancelled` | — |
| `Paused` | `Downloading`（经 resume）、`Cancelled` | `Done`/`Failed`/`Cancelled`（来自已退出的旧循环） |
| `Done`/`Failed`/`Cancelled` | — | 全部 |

`Paused` 行的拒绝项就是 P0.3 的修复点；末行的"拒绝全部"同时消掉 P0.4 的状态跳变和"完成撞取消"的竞态。
